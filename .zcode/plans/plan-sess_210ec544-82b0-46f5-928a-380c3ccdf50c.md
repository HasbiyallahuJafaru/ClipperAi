## Multi-user publishing the cheap way: per-user Buffer OAuth (one flow, all six networks)

Verified: Buffer client registration is self-serve (Buffer → Settings → API), OAuth is Authorization Code + PKCE against auth.buffer.com, refresh tokens via the `offline_access` scope (single-use, rotate on refresh). Each user connects their own Buffer account; their channels (TikTok/IG/YouTube/LinkedIn/Facebook/X) work through our existing publishing stack unchanged. The workspace key (`BUFFER_OWNERS`) stays as the fallback. MIT-licensed Open-Dispatch and the unlicensed socialmediascheduler remain reference-only for a possible direct-API expansion later — nothing copied.

### The user does first (5 minutes, no review process)
Register "YT-Clipper" in **Buffer → Settings → API** with redirect URI `https://ytclipper.xyz/oauth/return` (dev: `http://localhost:3000/oauth/return`), put `BUFFER_CLIENT_ID` / `BUFFER_CLIENT_SECRET` in Railway + `.env`.

### Backend
1. **Migration `008_accounts.sql`** — `connected_accounts` (one active per owner+provider, partial unique index like subscriptions): `owner, provider ('buffer' now; 'linkedin'|'youtube'|'threads' later), account_id, account_name, access_token, refresh_token, expires_at, created_at`. Plus `oauth_states(state pk, owner, provider, verifier, created_at)` for CSRF-safe PKCE.
2. **`oauth.py`** (new, small, publishing.py style, stdlib urllib):
   - `connect_url(owner, provider)` → auth.buffer.com/auth URL with random `state` row + S256 `code_challenge`.
   - `callback(state, code)` → validate state (≤10 min), exchange at auth.buffer.com/token, save the account.
   - `token_for(owner)` → the user's valid access token, refreshing (and rotating the single-use refresh token) when within 10 minutes of expiry; a failed refresh marks the row expired (UI → Reconnect). 401 during publish → one refresh + retry, else "reconnect" error.
   - # ponytail: tokens stored plaintext; encrypt at rest only if the threat model changes.
3. **`publishing.py`** — `channels(owner)`: with a connected account, list *their* Buffer channels via their token; without one, today's workspace view (unchanged for existing flows). `publish/send_queued`: sign requests with the owner's token when they have one, else the workspace key (still gated by `BUFFER_OWNERS`). `allowed()` becomes: connected account OR `BUFFER_OWNERS` listing.
4. **`jobs.py`** — the existing `send_posts` loop needs no change beyond calling through `oauth.token_for`; refresh sweep piggybacks there (only for accounts used/publishing soon — ponytail: refresh lazily on use, no dedicated sweeper).
5. **Routes** — `POST /api/publishing/connect/buffer` (authed → authorization URL), `POST /api/publishing/callback` (authed through the website proxy; the browser returns from Buffer with its Clerk session intact), `DELETE /api/publishing/connection` (disconnect; Buffer-side revoke happens in the user's Buffer settings).

### Website
6. `/settings/integrations`: "Connect Buffer" button → authorization URL; shows connected account + Disconnect; when missing, the publish UI nudges "Connect your Buffer account to publish".
7. New `/oauth/return` page: reads `?code&state`, POSTs through the signed-in proxy, shows connected / failed. Publish dialog and calendar unchanged (channels come from the user's own account automatically). Mobile needs no change (same API shape).

### Later (unchanged, not now)
Direct LinkedIn/YouTube/Threads for users who won't use Buffer — port from Open-Dispatch's MIT adapters into the same `connected_accounts` table. Meta/TikTok stay parked pending app reviews.

**Order:** migration + oauth.py + publishing wiring → routes → website page → fake + tests → all checks → commit/push. Live test after you register the Buffer app and connect your own account first.
